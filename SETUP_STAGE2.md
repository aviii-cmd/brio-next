# Brio Stage 2 — Projects Workspace — Setup & Release Notes

## What this release adds

The **Projects Workspace**: a full rebuild of the Projects area from a simple
CRUD list into a narrative-first case-study builder, per the Stage 2 PRD.

- **Projects Home** (`/dashboard/projects`) — grid/list views, status +
  type filters, search, Featured and Needs Polishing sections.
- **Project detail page** (`/dashboard/projects/:id`) — the opinionated
  Hero → Summary → Problem → Process → Results → Skills → Artifacts →
  Reflection structure, entirely inline-editable with silent autosave.
- **Timeline & Milestones**, **Artifact Gallery** (uploads + external
  links, categorized, captioned), **Skills & Technologies**, and typed
  **Tags** (Skill / Tech / Domain) for future faceted filtering.
- **Draft → Published → Archived** states, with a public, unauthenticated,
  mobile-friendly share page at `/p/:projectId`.
- **Project Readiness** scoring (Draft → Case study in progress →
  Portfolio-ready) based on section completion and evidence richness.
- A global command palette (**⌘K / Ctrl+K**) to search projects and create
  new ones, plus a **`c`** keyboard shortcut for "New project" and
  **⌘S / Ctrl+S** to force-flush autosave.
- The existing Skills module now actually syncs from project skills again
  (`skillService.syncFromProjects` existed in Stage 1 but was never called
  after a project write — it's now wired into create/update/autosave).

No existing Stage 1 tables, columns, or routes were removed or renamed.

## Required setup (do this once)

### 1. Run the migration

In the Supabase dashboard → **SQL Editor**, paste and run:

```
supabase/migrations/002_stage2_projects_workspace.sql
```

This is additive-only: it adds columns to `projects` (with safe defaults,
so existing rows are unaffected) and creates four new tables
(`project_milestones`, `project_artifacts`, `tags`, `project_tags`) with
RLS policies scoped through project ownership, plus a new
`project-artifacts` public storage bucket (25MB limit, images/video/PDF)
with folder-scoped upload/update/delete policies mirroring the existing
`avatars` bucket.

### 2. Environment variables

None. This release reuses the existing `VITE_SUPABASE_URL` /
`VITE_SUPABASE_ANON_KEY` — no new services or keys are introduced.

### 3. Let the router regenerate

`src/routeTree.gen.ts` is auto-generated by the TanStack Router Vite
plugin and is intentionally **not** hand-edited (see `src/routes/README.md`).
Two new route files were added:

```
src/routes/dashboard.projects.$projectId.tsx   →  /dashboard/projects/:id
src/routes/p.$projectId.tsx                    →  /p/:id  (public)
```

The first `npm run dev` or `vite build` after pulling this change will
pick these up automatically. Until that regeneration happens, your editor
may show a type error on the two `<Link to="/dashboard/projects/$projectId">`
call sites — this resolves itself once the route tree regenerates and is
not a real bug.

## Design decisions worth knowing about

- **`problem` / `action` / `result`** (Stage 1 columns) are reused as the
  Problem & Objectives / Solution & Process / Results & Metrics narrative
  fields rather than adding parallel new columns — this keeps existing
  project data intact and immediately visible in the new layout.
- **Skills & Technologies** on the project page is still the original
  `projects.skills` text array (feeds the Skills module, as required).
  The new **Tags** section (Skill/Tech/Domain) is a separate, lighter
  system purely for future faceted filtering (PRD §5.3) — it intentionally
  doesn't feed the Skills module, to avoid duplicating it.
- **Readiness score** shown on the project page is the full calculation
  (sections + milestones + artifacts + tags). The lighter progress bar on
  Projects Home cards is a cheaper approximation (narrative fields only)
  so the list view doesn't need N+1 queries per card.
- Publishing is reversible and does not delete anything; hard delete is a
  separate, explicitly-confirmed, destructive action reached from the
  project menu. Deleting a project also removes its uploaded files from
  storage (cover image + artifacts), not just the database rows.

## Known gaps / not implemented

- **Collaborative co-author versions** (PRD §8 edge case — each co-author
  maintaining their own narrative of a shared project) is a materially
  larger data-modeling feature (shared project identity across multiple
  owners) and was left out of this pass.
- **Saved views** (PRD "Nice to Have") aren't implemented — filters reset
  per session.
- Typed Tags aren't yet surfaced as filters *on Projects Home itself*
  (the picker and storage are fully wired on the project page); wiring
  them into the Projects Home filter rail is a small, isolated follow-up.
